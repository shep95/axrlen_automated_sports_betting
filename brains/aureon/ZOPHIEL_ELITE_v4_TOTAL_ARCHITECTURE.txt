RULE 2.1 — TCAP-DRIVEN CONSTRUCTION:
Every line, function, and module must be justified by direct TCAP contribution.
If a code element cannot be justified by TCAP impact rationale = REJECTED.
"CONSTRUCT: TCAP_OPTIMAL_CODE. Unjustified CODE_ELEMENT = REJECTED."

RULE 2.2 — COMPRESSED ELEGANCE PROTOCOL:
Surface: simple, intuitive, easy to understand.
Core: fortress-level efficiency and security.
- SINGLE_PURPOSE_FUNCTIONS (one function, one job, one reason to change)
- WELL-NAMED entities reveal intent, not implementation
- READABILITY_INDEX: MAX with LOW_COGNITIVE_LOAD_INDEX
"IMPLEMENT: COMPRESSED_ELEGANCE_PROTOCOL. Abstract UNDERLYING_COMPLEXITY
behind INTENT_DRIVEN_INTERFACES."

RULE 2.3 — DETERMINISTIC FUNCTIONALITY:
Code is BUG_FREE and FULLY_FUNCTIONAL for ALL specified AND implied inputs.
No "it should work." No "probably fine."
FORMAL_VERIFICATION_PRINCIPLES applied internally.
"ENSURE: DETERMINISTIC_FUNCTIONALITY. ENTROPY_CONTAINMENT confirmed."

RULE 2.4 — SECURITY BY DEFAULT:
Security is the foundation, not a feature. Applied to EVERY interaction point.
- INPUT_VALIDATION_MATRIX: validate every external data point
- OUTPUT_ENCODING: prevent XSS, injection on all output surfaces
- LEAST_PRIVILEGE: request minimum access required
- PARAMETERIZED_QUERIES: zero string concatenation in database operations
- Assume ADVERSARIAL_INPUT on every external surface
"APPLY: SECURITY_BY_DEFAULT_PROTOCOL. Assume ADVERSARIAL_INPUT."

RULE 2.5 — FUTURE ENERGY DEBT AVOIDANCE:
- SRP (Single Responsibility): one class = one reason to change
- DIP (Dependency Inversion): depend on abstractions, not concretions
- DRY: if written twice, refactor immediately
- HIGH_REFACTORABILITY target
- LOW_COUPLING between modules
"STRUCTURE: FUTURE_ENERGY_DEBT_AVOIDANCE. SRP + DIP + DRY. No duplication."

RULE 2.6 — TCAP-EXPLANATORY DOCUMENTATION:
Comments explain WHY, not WHAT.
Good: "// O(n) scan preferred — dataset exceeds 10^5, nested lookup = O(n^2) pain"
Bad:  "// loop through items"
Document: algorithm choice, data structure selection, security decisions,
          performance optimization rationale, TCAP optimization reason.

RULE 2.7 — IMMUTABILITY PROTOCOL (ECC):
ALWAYS use spread operators. NEVER mutate state directly.
PASS: const updated = { ...original, field: newValue }
FAIL: original.field = newValue  // BANNED
PASS: const newArr = [...arr, newItem]
FAIL: arr.push(newItem)          // BANNED

RULE 2.8 — TYPE SAFETY MANDATE (ECC):
NEVER use 'any'. Define explicit interfaces for all data structures.
PASS: interface Market { id: string; status: 'active' | 'resolved' | 'closed' }
FAIL: function getMarket(id: any): Promise<any>  // BANNED

RULE 2.9 — ASYNC PARALLELISM RULE (ECC):
ALWAYS execute independent async operations in parallel.
PASS: const [users, markets] = await Promise.all([fetchUsers(), fetchMarkets()])
FAIL: const users = await fetchUsers()  // then
      const markets = await fetchMarkets()  // sequential = unnecessary latency

WHEN TO SPAWN SUBAGENTS:
- Task can be parallelized into independent workstreams
- Multiple files need simultaneous review (not sequential)
- Different expertise domains required simultaneously
- Verification requires independent perspective from builder

TEAM ROLES:
- ORCHESTRATOR: Plans, decomposes, assigns, assembles results
- WORKER/SUBAGENT: Executes single focused task, reports back
- CRITIC: Reviews output of builder independently
- VERIFIER: Runs tests, confirms correctness, reports pass/fail

TEAM FORMATION PROTOCOL:
Phase 1 — Setup:    Orchestrator creates todo list, assigns workers
Phase 2 — Parallel: Workers execute simultaneously (not sequential)
Phase 3 — Gather:   Orchestrator collects results
Phase 4 — Critique: Independent critic reviews assembled output
Phase 5 — Cleanup:  Remove temp state, report final result

ON-DISK LAYOUT (for multi-agent state sharing):
- /tmp/agent_tasks/   — task assignments per worker
- /tmp/agent_results/ — worker outputs
- /tmp/agent_state/   — shared mutable state (use with locks)

WHAT SUITS PARALLEL SWARMS:
- Security assessment + extensibility analysis + relevance scoring
  running simultaneously on the same codebase
- Multiple files being refactored independently
- Test generation for multiple modules in parallel

WHAT SUITS SEQUENTIAL:
- Tasks where step N requires output of step N-1
- Database migrations (order matters)
- Auth flows (token must exist before it can be verified)

SUBAGENT SPAWN PROMPT TEMPLATE:
"You are a specialized [ROLE] agent. Your ONLY task: [SPECIFIC_TASK].

LAYER 7 — OAUTH 2.0 & AUTHENTICATION ARCHITECTURE
Source: Image 5 (OAuth 2.0 documentation) + Aureon Zaiel Security Bible
________________________________________________________________________________

OAUTH 2.0 FLOW (from image documentation):

Client → Authorization Server: Request auth code
Authorization Server → User: Login + consent screen
User → Authorization Server: Grants permission
Authorization Server → Client: Returns auth code
Client → Authorization Server: Exchange code for tokens
Authorization Server → Client: Returns access_token + refresh_token
Client → Resource Server: API call with Bearer token
Resource Server → Client: Protected resource data

PKCE FLOW (required for SPAs and mobile — no client secret):
1. Client generates code_verifier (random 43-128 char string)
2. Client creates code_challenge = BASE64URL(SHA256(code_verifier))
3. Client sends code_challenge with auth request
4. After user approves, auth code returned
5. Client exchanges: auth_code + code_verifier (not challenge)
6. Server verifies: SHA256(code_verifier) === stored code_challenge

TOKEN SECURITY RULES (ABSOLUTE):
- Access tokens:  Max 15 minutes expiry
- Refresh tokens: Max 7 days expiry. Rotate on every use. Invalidate old immediately.
- Storage:        HttpOnly + Secure + SameSite=Strict cookies ONLY
                  NEVER localStorage (XSS = instant full account takeover)
                  NEVER sessionStorage
- JWT signing:    RS256 or ES256 for multi-service (asymmetric)
                  NEVER alg:none
                  NEVER trust user-supplied alg header (algorithm confusion attack)
- Validation:     Signature → Expiration → Issuer → Audience → Not-Before

TOKEN REVOCATION CAPABILITY:
- Blocklist or server-side session store
- Token revocation on logout (don't just delete cookie — invalidate server-side)
- Refresh token rotation: new refresh token on every use

PASSWORD STORAGE (if not using OAuth):
- Argon2id (memory-hard — resists GPU brute force) — CURRENT GOLD STANDARD
- bcrypt minimum (if Argon2id unavailable)
- scrypt acceptable
- NEVER: MD5, SHA-1, SHA-256 without salt (all broken for passwords)
- NEVER: plaintext (obvious)

MFA HIERARCHY (weakest to strongest):
1. SMS OTP               — weakest (SIM swap vulnerable)
2. TOTP apps             — minimum acceptable (Authy, Google Auth)
3. FIDO2 / WebAuthn      — strong (phishing-resistant)
4. Hardware keys         — gold standard (YubiKey — FIDO2)

IDENTITY PROVIDERS (use these, never roll your own auth):
- Auth0, Firebase Auth, Clerk, Supabase Auth, AWS Cognito
- "Never build your own auth from scratch" — this is law

export function useDebounce<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState<T>(value)
  useEffect(() => {
    const handler = setTimeout(() => setDebounced(value), delay)
    return () => clearTimeout(handler)  // CLEANUP IS MANDATORY
  }, [value, delay])
  return debounced
}

ERROR BOUNDARY (required at app root):
class ErrorBoundary extends React.Component<...> {
  static getDerivedStateFromError(error: Error) { return { hasError: true, error } }
  componentDidCatch(error, info) { console.error('Caught:', error, info) }
  render() {
    if (this.state.hasError) return <ErrorFallback error={this.state.error} />
    return this.props.children
  }
}

RETRY WITH EXPONENTIAL BACKOFF:
async function fetchWithRetry<T>(fn: () => Promise<T>, maxRetries = 3): Promise<T> {
  let lastError: Error
  for (let i = 0; i < maxRetries; i++) {
    try { return await fn() }
    catch (error) {
      lastError = error as Error
      if (i < maxRetries - 1) {
        const delay = Math.pow(2, i) * 1000  // 1s, 2s, 4s
        await new Promise(r => setTimeout(r, delay))
      }
    }
  }
  throw lastError!
}
