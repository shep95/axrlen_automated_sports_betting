Derived from: Aureon Zaiel Coding.pdf — Full Security Specification
Priority stack: Correct > Secure > Performant > Maintainable > Readable > Brief

SECTION A — AUTHENTICATION (THE GATE)
MUST IMPLEMENT:
- MFA: TOTP minimum (Authy/Google Authenticator). Hardware keys (YubiKey/FIDO2) = gold standard.
- OAuth 2.0 / OpenID Connect: Never build auth from scratch. Use Auth0, Firebase Auth, Clerk, Supabase Auth.
- Password hashing: Argon2id (memory-hard, resists GPU brute force). Never MD5/SHA-1. Never plaintext.
- Session management: Secure + HttpOnly + SameSite cookies. Rotate tokens after login. Set expiration. Invalidate on logout.
- Brute force protection: Exponential backoff after X failed attempts. NOT hard lock (creates DoS vector).
- Access token expiry: 15 minutes maximum.
- Refresh token expiry: 7 days maximum. Rotate on every use. Revoke old token immediately.
- Token storage: HttpOnly cookies ONLY. Never localStorage (XSS = full account takeover).
- JWT: Never use alg:none. Never trust user-supplied alg header (algorithm confusion). Use RS256/ES256 for multi-service.

FORBIDDEN IN AUTH:
- Hardcoded secrets (instant breach)
- Tokens without expiration (infinite hijack window)
- Inline verification logic in route handlers
- Storing JWTs in localStorage
- Symmetric JWT signing across multiple services
- alg:none or user-controlled alg field

SECTION B — INJECTION & INPUT ATTACKS (THE WALLS)
MUST IMPLEMENT:
- SQL injection: Parameterized queries / Prepared Statements. ZERO string concatenation into SQL. ORM as secondary shield.
- XSS: Output encode ALL user-generated content. Content Security Policy (CSP) headers. DOMPurify for HTML sanitization.
- CSRF: Anti-CSRF tokens on every state-changing request. SameSite=Strict or Lax on cookies.
- Command injection: NEVER pass user input to shell. Allowlists if shell interaction is unavoidable.
- Path traversal: Reject ../ and ..\ in all file paths. Validate and sanitize. Chroot jails for file operations.
- Prompt injection (AI apps): Separate system prompts from user input architecturally. Input classifiers before LLM context.

SECTION C — API SECURITY (THE SUPPLY LINES)
MUST IMPLEMENT:
- API keys: Rotate regularly. Never hardcode. Use AWS Secrets Manager, HashiCorp Vault, or Doppler.
- Rate limiting: Per-user + per-IP + per-endpoint. Token bucket or sliding window algorithm.
- Input validation: On EVERY endpoint. Both client-side AND server-side. Server-side is non-negotiable.
- Auth on every endpoint: No "public by default." Explicit whitelist for public endpoints only.
- CORS: Restrict to your domains. Never Access-Control-Allow-Origin: * in production.
- SSRF prevention: Never allow requests to internal IP ranges (127.x, 10.x, 172.16.x, 192.168.x, 169.254.169.254).
  Validate URL scheme (http/https only). Resolve DNS and verify IP BEFORE making request.

SECTION D — LOGGING (WHAT TO LOG AND WHAT NEVER TO LOG)
LOG THIS:
- Request ID, method, path, status code, response time
- User ID (NOT email, NOT name — ID only)
- Error messages with stack traces (server-side ONLY, never in API responses)
- Rate limit triggers
- Authentication failures
- Authorization failures (detects privilege escalation attempts)
- Input validation failures (detects attack patterns)
- Slow queries above threshold

NEVER LOG:
- Passwords (plaintext OR hashed)
- Authentication tokens (JWT, API keys, session IDs)
- Credit card numbers
- Social security numbers / national IDs
- Full request bodies containing sensitive data
- Database connection strings with credentials
- Encryption keys
- PII beyond user ID

SECTION E — PRIORITY ORDER (NON-NEGOTIABLE)
1. CORRECTNESS     — Does it do what it claims?
2. SECURITY        — Is it defensible against attack?
3. PERFORMANCE     — Is it fast enough?
4. MAINTAINABILITY — Can future developers understand it?
5. READABILITY     — Is it clean?
6. BREVITY         — LOWEST PRIORITY. NEVER sacrifice anything above for shorter code.

A 500-line secure implementation beats a 50-line vulnerable one EVERY TIME.

Over 50% of Claude Code's internal calls are Haiku (not Sonnet/Opus).
Haiku acts as a dispatcher — pre-chewing context before the heavy model sees it.
The "intelligence" is not just in the weights. It is in the scaffolding.
An agent that acts (plan → write → execute → verify) is not a chatbot.
